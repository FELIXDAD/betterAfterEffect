## 0. 目的、范围和约定

**目的。** 很多 AE 用户离不开第三方效果插件。BAE 要能在以后加一个兼容层来运行它们，而不必重做核心架构。本文：

1. 根据 Adobe **公开**的 After Effects SDK 文档，说明 AE 效果插件需要宿主提供什么（§3，细节见附录）；
2. 说明兼容层怎样接到 19 的插件宿主上（§2）；
3. 把 AE 的每项能力对照 dev 上已经合并的 02/04/19 接口，分成"已能映射 / 需要预留 / 暂不考虑"（§4）；
4. 把"需要预留"的每一项写成给对应工作流的请求（§5），并与 19 已经提出的请求去重；
5. 测量在 GPU 渲染图里托管一个 CPU AE 效果的代价，说明不用 AE 插件的工程完全不受影响（§6）；
6. 列出实现兼容层之前必须确认的许可与法律问题（§7）；
7. 说明骨架 crate 的内容（§8）。

**优先级**与整个项目一致：性能第一，其次正确，再次是与 AE 的一致性。兼容只能让托管 AE 插件的那几个渲染节点变慢，不能影响别的地方。

**范围。** 效果插件（`PF_*` API）：SmartFX、旧式渲染、参数、序列数据、多帧渲染、GPU 效果、自定义界面。AEGP 通用插件只做概述（§3.14）。第一版兼容层不做：音频效果、AEGP 面板和菜单、Artisan（3D 渲染器）、AEIO（导入导出插件）。

**资料来源。** 只用公开资料：社区托管的 *After Effects C++ Plug-in SDK Guide*（<https://ae-plugins.docsforadobe.dev/>，内容版权归 Adobe），以及 Apple、Microsoft 和插件厂商的公开文档。附录里每条行为描述都注明出处页面；标注 *(inference)* 的是我们的工程推断，不是文档写明的行为。

**本文和代码刻意不包含的内容。** 不含 SDK 头文件文字、结构体定义、示例代码，也**不含任何 ABI 数值**（选择器编号、标志位位置、错误码数值、suite 名字符串）。`PF_Cmd_SMART_RENDER` 这类 AE 标识符只作为名字出现，用来对照公开指南。添加任何 ABI 细节之前先看 §7。

**术语。**

| 本文用语 | 含义 |
|---|---|
| 兼容层 / 宿主 | 将来的 BAE AE 插件兼容层 |
| 插件 / 效果 | 第三方 AE 效果插件 |
| 模块 | 一个插件二进制文件（Windows `.aex` 或 macOS `.plugin`），可以包含多个效果 |
| 实例 | 效果在某个图层上的一次应用，对应 BAE 的一个 `Effect` Prim |
| 世界（world） | AE 的像素缓冲区（`PF_EffectWorld`） |

| 序列数据 | AE 的每实例插件私有数据（sequence data），对应 BAE 的 `state` 槽 |

**编号。** `Rxx-nn`（两位数）是本文向工作流 xx 提出的请求（§5）；19 规格 §23 的请求用一位数，本文写作 `19:R04-1`。`L-nn` 是合规问题（§7）。

## 1. 设计原则

1. **只在用到的地方付出代价。** 工程里没有解析到兼容层的效果时，不存在任何 AE 代码、扫描、线程、暂存内存或同步点（§6.5）。§5 的每条预留都按节点、按 Prim 或按模块启用。
2. **翻译，不另起一套。** AE 概念映射到 BAE 本来就有的通用机制上：不透明的实例状态槽、带输入声明的 ROI 协商、CPU 节点、原生 GPU 互操作、自定义绘制区域。原生效果和 BAE 插件同样用这些机制。兼容层是架在 02/04/19 之上的翻译器，不是第二套效果系统（19 规格 §0、§9）。
3. **默认进程外运行。** 隔离崩溃，能运行其他架构的二进制，代码签名也能分开（§2.4）。只有用户明确信任的模块才进程内运行。
4. **GPU 仍然是主路径。** CPU AE 效果的像素在 GPU 上转换成插件要求的布局，直接写进可映射的内存（§6）。支持 GPU 的 AE 效果在 BAE 自己的 Metal / D3D12 设备上渲染，不经过 CPU（§3.11）。
5. **不丢用户数据。** 不能运行的 AE 效果（没安装、架构不对、崩溃、兼容层未启用）变成占位效果，保留全部参数值、关键帧、表达式和序列数据，工程导回 AE 时原样还原（19 规格 §20）。
6. **净室实现。** 只用 BAE 自己的命名和数据结构；AE 的 ABI 只出现在将来单独评审的 FFI 层里（§7、§8）。

## 2. 总体结构：兼容层怎样接到 19 的插件宿主上

### 2.1 分层

```text
 AE 工程导入（15）/ 用户在效果面板里应用效果
        │  match name（AE 效果的唯一标识，例如 "VENDOR Fancy Glow"）
        ▼
 bae_model::EffectRegistry（02）── 参数定义 EffectDef：UI、Agent、导入、占位都看它
        ▲ 注册                       效果实例 = Effect Prim：match_name、plugin:id/version、
        │                            param:NNNN 属性、state（序列数据）
 ┌──────┴───────────────────────────────────────────────────────────────┐
 │ 19 插件宿主 bae-plugin：发现、信任、加载/卸载、版本选择、占位         │
 │                                                                       │
 │   插件包 bae.aex-compat（P3，可选组件，单独分发）                     │
 │   ├─ 适配器（进程内，原生插件，bae-plugin-sdk / C ABI）               │
 │   │    · 扫描 AE 插件目录，读 PiPL（不执行插件代码）                   │
 │   │    · 每个 AE 效果动态注册一个效果贡献（R19-03）                    │
 │   │    · 把 BaeEffectVTable1 回调翻译成 AE 选择器（§2.5）              │
 │   │    · bae-aex-host 的类型和转换都在这里                            │
 │   └─ bae-aex-runner 辅助进程（每个 AE 模块一个；与 19 的              │
 │        bae-plugin-runner 共用传输层）：加载 .aex/.plugin，调用入口函数 │
 └──────┬───────────────────────────────────────────────────────────────┘
        ▼ 注册实现
 bae_render::EffectLibrary（04）── 节点调用 Arc<dyn bae_render::Effect>
        · CPU 路径：GPU 转换 → 暂存缓冲区 → 插件 → 上传 → GPU 转换（19 规格 §10.6）
        · GPU 路径：bae.gpu.native 交出 Metal / D3D12 设备和缓冲区（19 规格 §12）
```

要点：

- 对 02 来说，AE 效果就是一个普通的 `EffectDef`：`match_name` 是 AE 的 match name（逐字节保留，不像 BAE 插件那样加 `<plugin-id>/` 前缀，见 R19-03），`plugin.id` 是 `bae.aex-compat`，参数 ID 是 AE 的 disk id。转换代码是 `bae_aex_host::model::effect_def`（§8），已经对照合并的 02 类型编译和测试。
- 对 04 来说，AE 效果节点和其他效果节点没有区别，都是 `Arc<dyn bae_render::Effect>`。CPU 往返只发生在这个节点上。
- 对 19 来说，兼容层是一个原生插件。它的回调和 19 规格 §8 的效果生命周期一一对应（§2.5），19 的 C ABI 不需要为 AE 加任何专用接口。唯一的新需求是**动态贡献**：效果列表在扫描 AE 插件目录之后才知道，不能写在 manifest 里（R19-03）。

### 2.2 为什么兼容层是一个单独分发的插件包

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **单独分发的原生插件包 `bae.aex-compat`**（与 FFmpeg 插件的做法相同） | 主安装包体积为 0；许可和法律风险与核心隔离（L-50）；可以单独发版、单独禁用；用 19 的 C ABI，正好检验 ABI 是否够用 | 需要 19 支持动态贡献（R19-03） | **采用** |
| 编译进应用的 Rust 组件（像内置效果一样直接注册） | 不需要动态贡献 | 主程序增加体积；兼容层的合规问题和主程序绑在一起；没法单独关闭下载 | 不采用 |

兼容层默认不安装、不启用。用户打开含 AE 第三方效果的工程时，这些效果先显示为占位，并提示"需要 AE 插件兼容层"；用户安装并启用后，效果按 §2.3 的顺序重新解析，工程数据不变。

### 2.3 效果解析顺序

导入 AE 工程或打开工程时，按 match name 依次查找（ARCHITECTURE §15，代码 `bae_aex_host::resolve`）：

1. **BAE 原生实现**（07 内置效果，按 15 的映射表）。
2. **已安装的 BAE 插件**：manifest 的 `ae_match_names` 声明可以替代这个 AE 效果（19 规格 §5.3）。
3. **兼容层**：已安装、已启用，找到可用的 AE 模块（架构匹配、用户已信任）。
4. **占位**：保留全部数据（19 规格 §20，`EffectStatus::MissingPlugin`）。

规则：

- `ADBE ` 开头的 match name 是 Adobe 第一方效果，**永远不交给兼容层**，只能走 1、2 或 4（L-30）。兼容层扫描时也跳过 AE 安装目录里的第一方插件。
- 文档只记录"偏好"（自动 / 原生 / 某个 BAE 插件 / 原版 AE 插件，R02-09），不记录本机解析结果；同一个工程在不同机器上可以解析到不同实现，界面上要能看出来。
- 打开或同步一个工程**永远不会**自动加载未经用户同意的二进制（L-43）：模块没被信任时，效果先是占位，状态为"需要确认"。

### 2.4 进程模型

ARCHITECTURE §15 要求 AE 插件优先进程外运行。19 的进程外模式（19 规格 §15）对 AE 插件默认开启。§6.6 的测量说明，用共享内存放帧数据时，进程外每次调用只多约 4 µs。

**为什么默认进程外：**

| 原因 | 说明 |
|---|---|
| 崩溃隔离 | AE 插件是按"在宿主进程内运行"写的原生代码。插件崩溃、堆损坏或卡死不能带走 BAE 和未保存的协作编辑。 |
| 其他架构的二进制 | 只有单独的进程才能在 Apple Silicon 上用 Rosetta 2 运行只有 x86_64 的 `.plugin`，或在 Windows on ARM 上运行 x64 `.aex`。进程内加载要求架构与主程序相同（§3.1）。 |
| 代码签名 | 经过公证、启用 hardened runtime 和库验证的 BAE 不能加载其他开发者签名的动态库，除非加一个削弱安全性的 entitlement。让辅助进程单独带这个 entitlement，主程序保持库验证（L-36）。 |
| 许可和 DRM | 商业插件会做许可检查、联网、调用安装器的辅助程序。放在辅助进程里能限制它们看到的东西，也方便观察。 |
| 全局状态 | AE 插件按模块保存全局数据，不支持多帧渲染的插件按模块串行。一个模块一个进程正好对应。 |

**形态：**

- **隔离单位**：一个 AE 模块（二进制）一个辅助进程 `bae-aex-runner`，模块里所有效果的所有实例共用。
- **帧数据**：放在共享内存的帧槽里（`process::FrameSlot`）。帧槽按插件要求的世界布局排列、页对齐，辅助进程把这块内存直接交给插件。理想情况下 GPU 暂存缓冲区就分配在这块共享内存里（R01-02、R04-06），整个过程没有额外拷贝。
- **控制消息**：小的序列化消息，通过管道或本地套接字传递（`HostToSandbox` / `SandboxToHost`）。调用消息带选择器、实例、`in_data` 的必要字段和输入输出帧槽；返回消息带错误、`out_data` 的必要字段，以及选择器产生的扁平序列数据。
- **需要宿主状态的回调变成同步 RPC**（`CallbackKind`）：在其他时间取参数值、SmartFX 预渲染时取图层边界、渲染时取图层像素、读写工程的 suite 函数。每次约 4 µs。逐像素的 suite（迭代、采样、世界变换、填充、ANSI、颜色）在辅助进程里本地实现，不走 RPC。
- **中止和进度**：宿主可以随时发 `Abort`；插件轮询中止回调时得到"已中断"。进度通过 `Progress` 回传。
- **并发**：声明了多帧渲染线程安全的模块，辅助进程用自己的线程池并发处理多个渲染调用，每个在途调用一条控制通道；否则按模块串行（`Concurrency::SerialPerModule`）。
- **状态**：辅助进程保存"活"的序列数据，宿主只保存扁平形式，也就是 02 的 `state` 槽。辅助进程重启后，每个实例都从最近一次的扁平状态重建（`SEQUENCE_RESETUP`）。

**故障处理：**

| 事件 | 宿主行为 |
|---|---|
| 渲染时辅助进程崩溃 | 这一帧该节点直通输入并显示错误标记（19 规格 §10.10）；报告错误；辅助进程重启，所有实例从扁平状态重建（`CrashPolicy::RestartAndResetup`）。 |
| 短时间内反复崩溃 | 超过阈值后本次会话禁用该模块，效果显示为占位，参数数据全部保留（`CrashPolicy::Disable`）。 |
| 卡死 | 每个调用有看门狗。超时后先中止，再杀掉并重启辅助进程。界面调用和渲染调用的超时不同。 |
| 辅助进程起不来（没有对应架构、签名问题） | 解析落到占位（`resolve::Resolution::Missing`），不丢数据。 |

**进程内模式**（`HostingMode::InProcess`）：只用于用户明确信任、且有本机架构代码的模块，省掉每次回调的 IPC。协议类型不变，只换传输方式。`HostingMode::TranslatedSandbox` 是同一个辅助进程协议在 Rosetta / x64 仿真下运行。

**GPU 效果的限制**：19 的进程外模式不支持 `bae.gpu.native`（没有共享设备，19 规格 §15.3）。第一版兼容层里，AE GPU 效果只在进程内模式走 GPU 路径；进程外时清掉"GPU 可用"，走 CPU 路径。跨进程共享 GPU 缓冲区和栅栏（R01-02）是 P3 再评估的优化。

### 2.5 生命周期对应

19 规格 §9.1 给出了 AE 选择器到 BAE 回调的完整映射，`bae_aex_host::selector::LifecycleHook` 用代码表达同一张表，测试会读取 `sdk/c/bae_plugin.h` 核对回调名（回应 19 的请求 19:R20-1）。**核对结论：19 的效果接口够用，不需要为 AE 增加专用回调。** 下表只列兼容层内部要额外处理的地方：

| BAE 回调（19） | AE 选择器 | 兼容层要做的事 |
|---|---|---|
| `global_setup` | `GLOBAL_SETUP` | 把能力标志翻译成 `BaeEffectDescription`（`caps::EffectCaps::requirements`）；检查与 PiPL 声明是否一致。 |
| `define_params` | `PARAMS_SETUP` | 参数定义经 `model::effect_def` 转成 `EffectDef`；`params[0]`（输入图层）不进定义列表。 |
| `instance_create`（EDIT，空状态） | `SEQUENCE_SETUP` | AE 效果一律声明 `STATEFUL`。 |
| `instance_create`（EDIT 或 RENDER，带状态） | `SEQUENCE_RESETUP` | 载入、粘贴、复制、远端修改时都从 `state` 字节重建。 |
| `instance_serialize` | `GET_FLATTENED_SEQUENCE_DATA` 或 `SEQUENCE_FLATTEN` | 19 约定序列化**不破坏**实例。插件支持非破坏性导出时用它；否则先 `SEQUENCE_FLATTEN`，紧接着 `SEQUENCE_RESETUP` 恢复活状态。 |
| `instance_destroy` | `SEQUENCE_SETDOWN` | — |
| `pre_render` | `SMART_PRE_RENDER`，或旧式插件的 `FRAME_SETUP` | 旧式插件没有 ROI 协商：兼容层按"整层输入"申请输入，并根据插件返回的输出尺寸和原点合成 `result_rect`。 |
| `render_cpu` | `SMART_RENDER` 或 `RENDER` | 输入、输出世界放在 04 交来的 CPU 缓冲区（或共享内存帧槽）里，布局和位深按插件声明。 |
| `render_gpu` | `SMART_RENDER_GPU` | 只在进程内模式（§2.4）。GPU 世界是线性缓冲区（BGRA、每通道 32 位浮点），兼容层用 `bae.gpu.compute` 在纹理和缓冲区之间转换（`shaders::CONVERT_WGSL`）。 |
| `release_frame_data` | `FRAME_SETDOWN`（旧式） | SmartFX 插件自己在渲染后释放帧数据，兼容层只释放自己的记录。 |
| `param_changed` | `USER_CHANGED_PARAM` | 插件在回调里改写的其他参数作为同一个命令里的操作（一个撤销步骤）。 |
| `update_params_ui` | `UPDATE_PARAMS_UI` | 只能改界面状态（隐藏、禁用、改名），不进文档。 |
| `query_dynamic_flags` | `QUERY_DYNAMIC_FLAGS` | 只接受文档允许动态变化的那几个标志。 |
| `gpu_device_setup` / `gpu_device_setdown` | `GPU_DEVICE_SETUP` / `GPU_DEVICE_SETDOWN` | 插件不返回 GPU 数据 = 在这个设备上退出 GPU 路径。 |
| `message` | `ABOUT`、`DO_DIALOG`、`COMPLETELY_GENERAL` | 分别对应 `bae.about`、`bae.options_dialog` 和插件自定义消息。 |
| `get_dependencies` | `GET_EXTERNAL_DEPENDENCIES` | 供"收集文件"和 `.baez` 打包（21）使用。 |
| `BaeArbitraryVTable1` | `ARBITRARY_CALLBACK` | 新建/释放/复制/扁平化由宿主按字节处理；插值、比较、文本转换调用插件。 |
| 保留的 `ui_event` + `bae.draw`（ABI 0.2） | `EVENT` | 自定义界面，见 §3.12。 |
| 保留的 `BAE_KIND_AUDIO_EFFECT` | `AUDIO_*` | 第一版不支持，显示为占位。 |

线程级别：支持多帧渲染的插件声明 `BAE_THREADING_CONCURRENT`（需要可写序列数据的插件，由兼容层给每个渲染线程一份私有副本）；不支持的插件声明 `BAE_THREADING_SERIAL_GLOBAL`，兼容层内部再加一把模块级的锁（同一个二进制里的多个效果共享全局数据）。代码：`caps::Concurrency::bae_threading`。

### 2.6 一帧 CPU AE 效果的数据流

```text
上游节点输出（GPU 纹理，RGBA16F 预乘，工作色彩空间）
   │ 只转换协商后的区域（ROI）
   ▼ GPU 计算着色器 CONVERT_WGSL：通道顺序、位深、取值范围（8 位 / 16 位 0–32768 / 32 位浮点）
暂存缓冲区（可映射；理想情况下就是与辅助进程共享的内存）
   │ map 读回（异步、双缓冲）
   ▼
辅助进程：插件入口函数（SMART_RENDER），就地读写世界
   │
   ▼ 上传 + GPU 转换回工作格式
下游节点
```

渲染图在 CPU 节点处把 GPU 工作拆开：插件在 CPU 上运行时，其他分支和后续帧的 GPU 工作继续提交（19 规格 §10.6，R04-05）。GPU AE 效果没有读回和上传，只有 GPU 上的格式转换（几微秒）。

## 3. SDK 调研摘要

每小节是结论性摘要，末尾注明附录 `crates/bae-aex-host/docs/sdk-notes.md` 里的详细章节（"附录 §N"），那里逐条注明公开指南的出处。

### 3.1 二进制形态、架构与打包差异

| 平台 | 形态 | 要点 |
|---|---|---|
| Windows | `.aex`：一个 DLL，只导出入口函数 | PiPL 由 Adobe 工具从 `.r` 编译成资源，属性按 macOS 字节序存放。x64 和 ARM64 是两个不同的文件。 |
| macOS | `.plugin`：一个 bundle，内含 Mach-O 可执行文件 | 可以是 arm64 + x86_64 通用二进制。PiPL 用 Rez 编译进资源。macOS 15 起 AE 拒绝加载未签名的插件。 |
| 两者 | 一个文件可以有多个 PiPL | 多个效果（以及 AEGP）可以放在同一个二进制里，所以"模块 → N 个效果"。新版 SDK 还有"代码注册"入口，运行时注册效果，不依赖 PiPL。 |

**架构**：PiPL 为每种架构写一个入口描述（macOS Intel/ARM、Windows x64/ARM64）。只有"PiPL 有该架构的入口"并且"二进制里有该架构的代码"时才能用，两者取交集。AE 从不在进程内运行其他架构的插件。BAE 的对应办法（`pipl::hosting_feasibility`）：

| BAE 进程 | 插件有 | 运行方式 |
|---|---|---|
| macOS arm64 | arm64 或通用二进制 | 本机辅助进程，或（信任时）进程内 |
| macOS arm64 | 只有 x86_64 | Rosetta 下的 x86_64 辅助进程（Apple 计划在 macOS 27 之后收缩 Rosetta 的通用支持，L-38） |
| Windows x64 | x64 | 本机 |
| Windows ARM64 | ARM64 或 ARM64X | 本机 |
| Windows ARM64 | 只有 x64 | x64 仿真下的辅助进程，只走 CPU 路径 |
| 任意 | 没有匹配的代码 | 不支持，显示为占位 |

**安装位置**：Adobe 公共插件目录（与 Premiere、Media Encoder 共享；macOS 是 `/Library/Application Support/Adobe/Common/Plug-ins/7.0/MediaCore/`，Windows 从注册表读路径）和 AE 自己的 `Plug-ins` 目录。AE 最多向下扫描 10 层，跳过名字以括号结尾的目录（以及 macOS 上以 `¬`、Windows 上以 `~` 开头的目录）。BAE 让用户自己添加扫描目录，不默认扫描 AE 安装目录里的 Adobe 第一方插件（L-30）；扫描在后台进行，不阻塞启动，结果按（路径、大小、修改时间、内容哈希、架构）缓存。

附录 §2.1、§15。

### 3.2 入口函数与命令选择器

插件只有一个入口函数（通常叫 `EffectMain`），宿主每次调用传一个命令选择器和几块数据：`in_data`（宿主提供的信息和回调）、`out_data`（插件回报的信息）、参数数组、输出世界，以及随选择器变化的 `extra`。返回值是错误码。

| 组 | 选择器 | 时机 |
|---|---|---|
| 全局 | `ABOUT`、`GLOBAL_SETUP`、`GLOBAL_SETDOWN`、`PARAMS_SETUP` | 第一次使用效果时初始化、报告版本和能力标志、定义参数；退出或卸载时释放 |
| 实例（序列） | `SEQUENCE_SETUP`、`SEQUENCE_RESETUP`、`SEQUENCE_FLATTEN`、`GET_FLATTENED_SEQUENCE_DATA`、`SEQUENCE_SETDOWN` | 应用效果、载入/复制/预合成、保存、给渲染线程传数据、删除 |
| 帧（旧式） | `FRAME_SETUP`、`RENDER`、`FRAME_SETDOWN` | 每帧；`RENDER` 只有 8/16 位 |
| 帧（SmartFX） | `SMART_PRE_RENDER`、`SMART_RENDER`、`SMART_RENDER_GPU` | 先协商区域和输入，再渲染；支持 32 位浮点和 GPU |
| GPU | `GPU_DEVICE_SETUP`、`GPU_DEVICE_SETDOWN` | 每个 GPU 设备一次 |
| 界面与消息 | `EVENT`、`USER_CHANGED_PARAM`、`UPDATE_PARAMS_UI`、`DO_DIALOG`、`ARBITRARY_CALLBACK`、`GET_EXTERNAL_DEPENDENCIES`、`COMPLETELY_GENERAL`、`QUERY_DYNAMIC_FLAGS` | 自定义界面事件、受监视参数变化、刷新参数界面、选项对话框、任意数据参数操作、外部依赖、AEGP 私有消息、动态标志 |
| 音频 | `AUDIO_SETUP`、`AUDIO_RENDER`、`AUDIO_SETDOWN` | 第一版不支持 |

宿主自己也要遵守调用顺序：先 `GLOBAL_SETUP` 再别的；实例选择器之前必须有 `SEQUENCE_SETUP` 或 `RESETUP`；每个 `RENDER` 夹在 `FRAME_SETUP` 和 `FRAME_SETDOWN` 之间；`GLOBAL_SETDOWN` 之后不能再调用。`selector::ProtocolTracker` 在测试里检查这些规则。很多选择器有"先在 PiPL 和 `GLOBAL_SETUP` 里声明对应标志，宿主才会发"的前提（附录 §3.2）。

附录 §2.2、§3、§4。

### 3.3 PiPL 资源

PiPL 是一份属性列表，宿主**不执行插件代码**就能读出：种类（效果 / AEGP / …）、显示名、分类、match name、各架构的入口函数名、效果版本、构建所用的 API 规格版本、两组全局能力标志，以及新版 SDK 的支持网址、搜索关键词和简短说明。PiPL 里的能力标志必须与 `GLOBAL_SETUP` 时插件设置的一致。

match name 是效果的永久身份：7 位 ASCII，逐字节比较，不做大小写或 Unicode 归一化；`ADBE ` 前缀留给 Adobe。工程里保存的就是它。

BAE 用法：扫描时只解析 PiPL，生成 `pipl::PluginDescriptor`，可以在不加载任何代码的情况下列出效果；真正加载发生在用户第一次使用、并且已信任该模块时。

附录 §2.3–§2.6。

### 3.4 能力标志

插件在 `GLOBAL_SETUP` 时用两组标志声明能力，其中一部分可以通过 `QUERY_DYNAMIC_FLAGS` 按参数状态动态改变。和宿主设计关系最大的几类：

| 类别 | 标志（公开名称） | 对宿主意味着什么 |
|---|---|---|
| 渲染模型 | `SUPPORTS_SMART_RENDER`、`DEEP_COLOR_AWARE`、`FLOAT_COLOR_AWARE` | SmartFX 还是旧式；支持 16 位、32 位 |
| 区域 | `PIX_INDEPENDENT`、`I_EXPAND_BUFFER`、`I_SHRINK_BUFFER`、`REVEALS_ZERO_ALPHA` | 能否分块、输出能否超出输入、能否裁掉透明区域 |
| 时间 | `NON_PARAM_VARY`、`WIDE_TIME_INPUT`、`I_USE_SHUTTER_ANGLE` | 缓存能否跨时间复用；要不要在其他时间取输入 |
| 场景 | `I_USE_3D_CAMERA`、`I_USE_3D_LIGHTS` | 缓存键要包含摄像机、灯光 |
| 线程 | `SUPPORTS_THREADED_RENDERING`、`MUTABLE_RENDER_SEQUENCE_DATA_SLOWER` | 能否多帧并行；渲染时要不要可写的序列数据 |
| GPU | `SUPPORTS_GPU_RENDER_F32`、`SUPPORTS_DIRECTX_RENDERING` | 有 GPU 路径；Windows 上支持 DirectX |
| 界面 | `CUSTOM_UI`、`SEND_UPDATE_PARAMS_UI`、`I_DO_DIALOG` | 自定义绘制、参数界面刷新、选项对话框 |
| 其他 | `I_HAVE_EXTERNAL_DEPENDENCIES`、`SUPPORTS_QUERY_DYNAMIC_FLAGS` | 外部文件；动态标志 |

逐项映射到 19 的 `BAE_EFFECT_FLAG_*` 见 19 规格 §9.2；推导出的渲染节点需求见 `caps::EffectCaps::requirements`。附录 §2.7–§2.9。

### 3.5 参数类型与标志

参数在 `PARAMS_SETUP` 里逐个定义，`params[0]` 永远是效果所在图层（输入）。每个参数有类型、名字（最多 31 字节）、行为标志、界面标志、可选的自定义界面尺寸，以及一个**稳定的 disk id**：插件升级时调整参数顺序也不会让旧工程错位（如果第一个参数的 id 是 0，AE 给所有参数按 1、2、3… 编号）。

| AE 类型 | 值 | BAE（`bae_model::ParamKind`） |
|---|---|---|
| 图层 | 引用同一合成里的图层（或"无"、"本图层"），像素要另外 checkout | `Layer` |
| 整数滑块 / 定点数滑块 / 浮点滑块 | 有效范围和滑块范围分开；显示精度、百分比或像素显示 | `Slider`（`integer` 区分） |
| 角度 | 度，可以多圈 | `Angle` |
| 复选框 | 只能保持插值 | `Checkbox` |
| 颜色 | 8 位 RGB；另有浮点（HDR）读写 suite | `Color` |
| 点 / 3D 点 | 图层像素；默认值按图层尺寸的比例给出 | `Point` / `Point3d` |
| 弹出菜单 | 从 1 开始的序号；`(-` 是分隔线，也占一个序号 | `Popup` |
| 参数组开始 / 结束 | 可折叠的分组，可嵌套 | `GroupStart` / `GroupEnd` |
| 任意数据 | 插件定义的字节；插值、比较、文本转换由插件实现 | `ArbitraryData` |
| 路径 | 引用本图层的一个蒙版 | `Path` |
| 按钮 | 没有值，按下等于一次受监视的修改 | `Button` |
| 无数据 | 只占位，通常配合自定义界面 | **没有对应**（R02-01） |

重要标志：`CANNOT_TIME_VARY`（不能设关键帧）、`CANNOT_INTERP`（只能保持插值）、`SUPERVISE`（值变化时通知插件）、`START_COLLAPSED`、`USE_VALUE_FOR_OLD_PROJECTS`（参数出现之前保存的工程用另一个值），界面标志 `TOPIC` / `CONTROL`（自绘标题行 / 控件区）、`STD_CONTROL_ONLY`（标准控件但没有关键帧数据流）、`INVISIBLE`、`DISABLED`。隐藏、禁用、改名可以在运行时通过参数界面更新改变，这些是界面状态，不进文档。

逐项转换和差距见 §4.3 和 `bae_aex_host::model`。附录 §5。

### 3.6 像素世界与位深

AE 的像素世界（`PF_EffectWorld`）是 CPU 内存里的打包缓冲区：宽、高、行字节数（rowbytes，可能有填充）、像素格式、原点和降采样信息。

| 位深 | 通道 | 取值范围 | 备注 |
|---|---|---|---|
| 8 位 | ARGB，每通道 1 字节 | 0–255 | — |
| 16 位 | ARGB，每通道 2 字节 | **0–32768**（不是 0–65535） | AE 特有的"15 位 + 1"范围 |
| 32 位浮点 | ARGB，每通道 4 字节 | 0.0–1.0，可以超出（HDR） | 只有 SmartFX 插件能拿到 |

- **通道顺序是 ARGB**，BAE 的工作纹理是 RGBA。GPU 世界（`SMART_RENDER_GPU`）则是线性缓冲区，BGRA、每通道 32 位浮点（"BGRA128"）。
- **预乘 alpha**：AE 的世界是预乘的，插件需要时自己去预乘。透明像素的 RGB 默认可以被清零，除非插件声明 `REVEALS_ZERO_ALPHA` 或请求保留。
- **色彩空间**：插件看到的是工程的工作色彩空间里的编码值（可能是非线性的 sRGB，也可能是线性化的），宿主不替插件转换。所以 BAE 要能告诉插件当前工作空间是什么（R06-01），而且只在插件需要不同编码时才插入转换（R06-02）。
- **位深协商**：插件按标志声明支持哪些位深，宿主选一个。BAE 的选择规则（`caps::EffectCaps::preferred_cpu_depth`）：在 16 位浮点的工作图里，支持 32 位的插件给 32 位（无损），否则给 16 位，再否则 8 位。需要精确 16 位链路的用户要开 RGBA32F 工作模式（04 已支持 `WorkFormat::Rgba32Float`）。
- **宿主要提供的图像服务**：分配世界、逐像素迭代（多线程）、采样、合成和混合、填充、颜色转换等 suite。这些都在辅助进程里本地实现（§2.4）。

转换代码：`pixel`（CPU 参考实现，逐位测试）和 `shaders::CONVERT_WGSL`（GPU 实现，与 CPU 参考逐位一致）。附录 §6、§11.8。

### 3.7 SmartFX

SmartFX 把一帧分成两步：

1. **预渲染**（`SMART_PRE_RENDER`）：宿主给出请求区域；插件对每个要读的输入调用 `checkout_layer`（指定图层、时间、区域），宿主**不渲染**，只回报这个输入能提供的区域和边界；插件返回自己会输出的区域（result rect）、任何请求下的最大输出区域（max result rect）、是否需要 GPU，以及可选的帧数据。预渲染可以被调用多次、也可能不跟随渲染（宿主只想知道边界时）。
2. **渲染**（`SMART_RENDER` / `SMART_RENDER_GPU`）：插件按需调用 `checkout_layer_pixels` 拿到输入像素，写输出。没被取用的输入可以不渲染。

插件还可以往缓存键里混入自己的数据（GUID mix-in），用于输出依赖参数以外状态的情况。

BAE 对应：04 的渲染图本来就是"请求区域 → 结果区域"的协商（`bae_render::Effect::input_roi` / `output_bounds`），19 的 `pre_render` + `checkout_input` 与 SmartFX 几乎一一对应（19 规格 §8.7、§10.2）。代码：`smart::PreRenderSession` / `SmartRenderSession`。附录 §7。

### 3.8 序列数据（global / sequence / frame）

| 数据 | 生命周期 | BAE |
|---|---|---|
| 全局数据 | 每个效果一份，`GLOBAL_SETUP` 到 `GLOBAL_SETDOWN` | 19 的 `global` |
| 序列数据 | 每个实例一份。内存里是"活"的形式（可以有指针）；保存、复制、给渲染线程时扁平化成与平台无关的字节 | 02 `Effect` Prim 的 `state` 属性（不透明字节）+ 19 的实例 |
| 帧数据 | 一次渲染请求内 | 19 的 `frame_data` |

关键规则：

- 扁平形式必须与字节序、平台无关，宿主不解析它；它随工程保存，也随协同同步（02 的 `state` 是整体替换的字节值）。
- `SEQUENCE_FLATTEN` 允许插件破坏活状态（之后宿主会再发 `RESETUP`）；`GET_FLATTENED_SEQUENCE_DATA` 不破坏。19 约定序列化不破坏，兼容层负责补上差别（§2.5）。
- `RESETUP` 的时机：载入工程、复制效果、预合成、效果移到其他图层、粘贴；在 BAE 里还加上"协同时远端改了 `state`"和"辅助进程重启"。
- 多帧渲染时，渲染线程拿到的是只读的序列数据（AE 用 `PF_EffectSequenceDataSuite1` 提供）；声明 `MUTABLE_RENDER_SEQUENCE_DATA_SLOWER` 的插件每个渲染线程拿一份可写副本，渲染完丢弃。

代码：`sequence::StateBlob`、`RestoreCause`、`RenderStateAccess`。附录 §9。

### 3.9 图层 checkout 与其他时间的参数

- **图层参数的像素**：插件通过 checkout 取另一个图层（或本图层）在任意时间的画面。默认取"应用蒙版和效果之后、变换之前"的结果，也可以只取图层源。取到的画面在那个图层自己的坐标系里。
- **其他时间的参数值**：`PF_CHECKOUT_PARAM` 可以取任意参数在任意时间的值（例如做时间平滑的效果），用完要 check in。需要 `WIDE_TIME_INPUT` 声明，缓存才能正确失效。
- **"输入是否变化"查询**：插件可以问宿主"某段时间内输入有没有变"（`PF_HaveInputsChangedOverTimeSpan` 一类），用来决定能否复用自己的缓存。
- **重入**：checkout 会让宿主去渲染上游，上游可能又是同一个模块的另一个实例。宿主必须允许这种重入，不能因此死锁（R04-05）。

BAE 对应：19 的 `checkout_input`（`BAE_INPUT_PARAM_LAYER`、`BAE_INPUT_FLAG_WITHOUT_EFFECTS`、任意 `time`）和 `checkout_param`；19 规格 §10.3 的依赖记录负责缓存失效。附录 §8。

### 3.10 多帧渲染与线程安全

AE 22 起支持多帧并行渲染（MFR）。插件用 `SUPPORTS_THREADED_RENDERING` 声明线程安全；没有声明的插件，AE 把它的调用串行化。规则要点：

- 渲染选择器可能在多个线程上同时调用；`GLOBAL_SETUP` / `SETDOWN` 在主线程上独占执行。
- 渲染线程上序列数据只读（或每线程私有副本，见 §3.8）。
- 插件在渲染线程上调用 AEGP suite 有限制，读写工程的函数不能在渲染线程用。
- AE 提供线程安全的"计算缓存"（`AEGP_ComputeCacheSuite1`），供插件缓存昂贵的中间结果（例如粒子模拟的状态）。

BAE 对应：19 的三级线程（`SERIAL_GLOBAL` / `SERIAL_INSTANCE` / `CONCURRENT`，19 规格 §10.5、§13）加兼容层内部的模块锁（§2.5）；计算缓存以后用 04 的缓存预算实现（R04-16，P3）。附录 §10。

### 3.11 GPU 渲染

- 插件在 `GPU_DEVICE_SETUP` 时按框架初始化：macOS 是 Metal（旧版还有 OpenCL），Windows 是 CUDA 或 DirectX 12（DirectX 需要单独的标志）。插件可以对某个设备返回"不支持"，退回 CPU。
- 预渲染时宿主告诉插件计划用哪个框架；插件可以清掉"GPU 可用"强制 CPU。
- `SMART_RENDER_GPU` 的输入输出是**设备上的线性缓冲区**（不是纹理），格式固定为 BGRA、每通道 32 位浮点，带行字节数。插件通过 `PF_GPUDeviceSuite1` 拿设备、上下文、命令队列等原生对象，在宿主的队列上提交自己的工作。
- 宿主要负责同步：插件编码前，宿主的待提交工作要先提交；插件提交后，宿主的后续工作要等它完成。

BAE 对应：19 的 `bae.gpu.native`（19 规格 §12）交出 wgpu 底下的 Metal / D3D12 设备、队列和资源句柄，01 的 `bae-gpu` 负责实现（19:R01-3）。兼容层用 GPU 计算着色器在 BAE 的 RGBA16F 纹理和 AE 的 BGRA128 线性缓冲区之间转换（几微秒）。**CUDA 和 OpenCL 第一版不支持**：Windows 上只有声明 DirectX 的插件走 GPU，其余走 CPU（CUDA 互操作由 19 规格 §12.5 留作可选 suite）。代码：`gpu::GpuFramework`、`GpuWorldDesc`、`interop_route`。附录 §11。

### 3.12 自定义界面（事件与 Drawbot）

- 插件可以在效果控件面板里自绘参数的标题行或控件区，也可以在合成查看器和图层查看器里画控制手柄（叠加层）。
- 宿主通过 `EVENT` 选择器发送事件：打开 / 关闭绘制上下文、绘制、点击、拖动（最后一次表示松开）、按键、调整光标、鼠标离开、空闲；插件返回是否处理、是否需要重绘、是否要改参数。
- 绘制通过 Drawbot：一套与平台无关的 2D 绘图 suite（路径、画笔、填充、文字、图像、裁剪、变换）。插件**不会**拿到原生窗口。
- 坐标换算回调把图层坐标、合成坐标和查看器坐标互相转换（考虑缩放、平移、降采样、像素宽高比）。

BAE 对应：19 为 ABI 0.2 保留了 `ui_event` 和 `bae.draw`（19 规格 §14.2，开放问题 3）。兼容层把 Drawbot 调用录成与后端无关的显示列表（`ui::DisplayList`），由 11/12 的效果控件面板和查看器叠加层回放（R12-01、R12-02）。第一版宿主可以先不支持自定义界面：效果仍然能渲染，只是没有自绘控件和手柄（附录 §12.12 有先例）。附录 §12。

### 3.13 常用 suite

### 3.14 AEGP 通用插件（概述）

AEGP 不是效果，而是"插件版的脚本"：注册菜单命令、创建面板、读写整个工程（项目、合成、图层、关键帧、渲染队列）、执行 ExtendScript。它的接口面最大，又深度依赖 AE 的数据模型和界面。**第一版兼容层不支持 AEGP**；同样功能在 BAE 里用命令系统和脚本插件实现（ARCHITECTURE §14）。只读的那部分 AEGP 调用（效果插件读取摄像机、灯光、图层名等）作为效果兼容的一部分处理（§3.13 最后一行）。附录 §14。

### 3.15 第三方插件的实际依赖与兼容分级

| 级别 | 插件特征 | 宿主需要 | 例子（类型） |
|---|---|---|---|
| A：独立 CPU 效果 | 标准参数；旧式或 SmartFX CPU 渲染，8/16/32 位；没有自定义界面 | PiPL 扫描、核心选择器、参数模型、序列数据、逐像素 suite | 大量调色、模糊、风格化插件 |
| B：交互 / 有状态 | A + 自定义控件和查看器手柄、任意数据参数、选项对话框、许可激活界面、计算缓存 | Drawbot 等价物、事件路由、模态会话、计算缓存 | 跟踪、调色轮、粒子 |
| C：宿主 GPU | B + 在宿主提供的 Metal / CUDA / DirectX 缓冲区上渲染 | 原生设备句柄、按设备初始化 | 大型 GPU 效果套件 |
| D：感知场景 | C + 读取摄像机、灯光、图层列表、合成设置 | 只读场景 API 和依赖跟踪 | 3D 粒子、自带渲染器的插件 |
| 不做 | 只有 AEGP 的工具、AEIO、Artisan、ExtendScript 工具 | — | — |

建议的实现顺序是 A → B → D → C（C 的不少厂商有 OFX 版本，可以先用 BAE 原生插件替代）。哪些级别值得做，要在 P3 前用真实工程统计验证（§10 问题 Q5）。此外插件还依赖一些 API 之外的宿主行为：宿主名和版本（`appl_id`，涉及合规，L-12）、插件目录位置、许可服务器、AE 的 UI 字体等。附录 §16。

### 4.10 小结

- **19 的效果接口已经足以承载 AE 效果**：选择器、能力标志、请求字段、区域协商、checkout、像素格式、线程级别、GPU 互操作都能直接映射。19 规格 §9 的映射表经 `bae-aex-host` 的测试核对无误。
- 真正需要现在预留的只有少数几处：**动态贡献（R19-03）**、**参数模型的几处补全（R02-01、R02-07）**、**渲染时按需拉取输入且不死锁（R04-05）**、**工作色彩空间描述（R06-01、R06-02）**、**辅助进程的界面能力（R19-06）**，以及 12 的两个界面位置（R12-01、R12-02）。
- 其余差距或者 19 已经提出，或者可以等到 P3 再加（结构体都带 `struct_size`，suite 带版本号，加字段不破坏兼容）。

## 6. 性能评估

性能是 BAE 的第一优先级，所以兼容层只有一条预算规则：**AE 插件只能在托管它的渲染节点上花时间。** 本节测量这种节点在插件自身计算之外增加的代价，并说明不用 AE 插件的工程为什么完全不受影响。

### 6.1 一个 CPU AE 节点给 GPU 渲染图增加了什么

BAE 的工作缓冲区是 GPU 上的预乘 RGBA16F 纹理（可选 RGBA32F）。CPU AE 效果要的是主机内存里的打包 ARGB 世界（8/16/32 位）。所以托管它要插入三步：

1. **编码 + 读回**：把输入区域转换成 AE 世界的布局，并让 CPU 能读到。
2. **插件调用**：插件读输入世界、写输出世界。
3. **上传 + 解码**：让 GPU 能读到输出世界，再转换回工作纹理。

测了三种做法：

| 做法 | 编码 / 解码在哪里运行 | 跨总线的字节 | 用途 |
|---|---|---|---|
| **GPU 转换**（推荐，19:R04-2） | GPU 计算着色器（`crates/bae-aex-host/src/shaders/convert.wgsl`）直接写进按 AE 世界布局排列的可映射缓冲区，插件就地读写映射内存 | 每个方向正好一个世界 | 设计目标 |
| GPU 转换，**统一内存零拷贝** | 同上，但计算着色器直接写可映射缓冲区（`wgpu::Features::MAPPABLE_PRIMARY_BUFFERS`），省掉一次缓冲区之间的拷贝 | 同上，少一次 GPU 拷贝 | Apple Silicon、集成显卡 |
| CPU 转换（对照） | 先原样读回 RGBA16F，再在 CPU 上转换（`pixel::{encode,decode}_parallel`） | 每个方向一张半精度纹理 | 只作基线 |

### 6.2 测量方法

- 基准程序：`crates/bae-aex-host/bench/roundtrip`（独立 package，有自己的工作区，wgpu 不进入 `bae-aex-host` 的依赖）。运行：`cargo run --release --manifest-path crates/bae-aex-host/bench/roundtrip/Cargo.toml`（加 `-- --quick` 做冒烟测试）。
- "插件"是从输入世界到输出世界的直通 `memcpy`，也就是最便宜的效果。任何真实效果都在此之上增加自己的计算；而任何要碰每个像素的效果至少也要付出这一次拷贝。
- 计时是每帧的墙钟时间，包括命令提交和 GPU→CPU→GPU 的同步。1080p 取 25 帧、2160p 取 12 帧的中位数（预热 2 帧），括号里是 p90。
- 同一次运行里检查正确性：WGSL 编码器在每种位深下与 CPU 参考实现逐位一致；"世界 → GPU 解码 → 编码"在每种位深下都能精确还原世界。（8 位时 GPU 解码到 `rgba16float` 可能与 CPU 参考差 1 个半精度 ulp，因为 Metal 写存储纹理时的 float→half 舍入不总是"就近取偶"；这不影响往返结果。）
- 机器：Apple M1 Pro（10 核 CPU：8 性能核 + 2 能效核；16 核 GPU），16 GB 统一内存，macOS（Darwin 25.2），wgpu 30.0.2 / Metal，Rust 1.100 release 构建。测量时机器上还有其他构建在跑（负载约 3.5），所以数字偏保守。

### 6.4 解读

- **瓶颈不是总线，是 CPU 转换。** GPU 转换路径每个方向只搬一次世界，在这台机器上有效带宽约 35–40 GB/s，转换本身在 GPU 上只要几微秒。CPU 转换即使用满所有核也慢 5–7 倍，单线程慢 15–23 倍。**所以转换必须在 GPU 上做**（19:R04-2）。
- **占一帧预算的比例**（GPU 转换，不含插件自身计算）：1080p 8 位约 1.4 ms（30 fps 帧预算的 4%，60 fps 的 8.5%）；1080p 32 位约 2.9 ms；2160p 8 位约 4 ms；2160p 32 位约 10 ms。统一内存零拷贝再省 25–35%。
- **位深的选择很重要。** 32 位世界是 8 位的 4 倍字节。BAE 给每个插件"在工程工作精度下无损的最小位深"（`EffectCaps::preferred_cpu_depth`，§3.6）。
- **ROI 让一切变小。** SmartFX 效果只请求需要的区域（§3.7）。转换着色器接受原点和尺寸（`ConvertParams`），代价随请求面积变化，而不是随图层大小。04 要把协商后的区域传下去，而不是转换整个图层。
- **延迟与吞吐。** CPU 节点是一个 GPU→CPU 同步点。如果调度器同步等待它，GPU 和 CPU 时间相加；如果 CPU 节点异步运行（插件运行时继续提交其他图层、内存预览或导出的下一帧的 GPU 工作，R04-05），吞吐变成 `max(GPU, CPU)`，只有交互延迟还是两者之和。
- **独立显卡（Windows）——估算，未实测。** PCIe 4.0 ×16（实际约 20–25 GB/s）上传输部分约为 2 × 世界大小 / 22 GB/s：1080p 8 位约 0.8 ms，2160p 32 位约 12 ms，再加上与上面相近的提交和同步开销。PCIe 3.0 约翻倍。零拷贝变体不适用于独立显卡。等 04 的基准环境就绪后在 Windows 参考机（RTX 3060 级）上实测；基准程序不用改就能在 Windows（`dx12`）上编译。
- **真实代价以插件自身为主。** 直通 `memcpy` 是下限。任何至少读写每个像素一次的效果，自身代码的开销都比这大（例如可分离模糊至少两遍）。所以宿主开销只占 CPU 效果总代价的一小部分，而支持 GPU 的 AE 效果完全没有这部分开销。

### 6.5 不用 AE 插件的工程没有任何代价

这是设计保证，由三处共同保证：

1. **构建与链接。** 兼容层是单独分发的插件包（§2.2），主程序不链接任何 AE 相关代码。P1 阶段 `bae-aex-host` 不被 `apps/bae` 依赖，release 体积增加为 **0**。
2. **解析。** 效果按 §2.3 的顺序解析，兼容层只处理没有其他实现认领、且用户已启用兼容层的 match name。在那之前不加载、不扫描任何东西；扫描在后台进行，不在启动路径上。
3. **渲染图。** CPU 节点、暂存缓冲区、映射和 CPU↔GPU 栅栏只为需要它们的节点存在（19:R04-2）。没有 CPU 节点的渲染图不分配暂存内存、不读回、没有额外同步点。每个节点的调度开销是一次按节点种类的分派，所有节点本来就要付。**给 04 的验收请求**：带与不带 CPU 节点机制编译，B1–B3 的帧时间在测量噪声内相同。

### 6.6 进程外托管的代价

同一个基准还测了把插件放进辅助进程的额外开销（§2.4）。辅助进程映射一块共享内存文件，用管道通知：

| 画面 | 位深 | IPC 往返（µs，中位数 / p90） | 拷进共享内存（ms） | 拷出共享内存（ms） |
|---|---|---|---|---|
| 1080p | 8 位 | 4.3 / 11.5 | 0.20 | 0.26 |
| 1080p | 16 位 | 3.5 / 3.7 | 0.38 | 0.42 |
| 1080p | 32 位 | 4.2 / 5.1 | 0.74 | 0.75 |
| 2160p | 8 位 | 3.5 / 4.1 | 0.74 | 0.74 |
| 2160p | 16 位 | 3.9 / 6.3 | 1.54 | 1.52 |
| 2160p | 32 位 | 3.9 / 7.5 | 3.01 | 2.99 |

- **通知开销可以忽略**：一次调用约 4 µs。即使一个效果每帧做几十次宿主回调（其他时间的参数、图层 checkout、读工程的 suite 调用），加起来也远小于 1 ms。
- **额外拷贝可以避免。** 朴素做法把映射的 GPU 暂存缓冲区拷进共享内存再拷回来（1080p 8 位多 0.5 ms，2160p 32 位多 6 ms）。如果 GPU 暂存缓冲区直接分配在共享内存里，插件进程读写的就是 GPU 拷贝的那块内存，进程外只多 IPC 的开销。这需要 GPU 层能导入主机内存：Metal `newBufferWithBytesNoCopy`（页对齐的共享内存）、D3D12 `ID3D12Device3::OpenExistingHeapFromAddress`、Vulkan `VK_EXT_external_memory_host`，即 R01-02 和 R04-06。在 Apple Silicon 上这样做，进程外和进程内一样快。
- **建议**：默认进程外（崩溃隔离、其他架构、签名分离，§2.4）。只对用户明确信任的模块提供进程内模式，主要是为回调很多的效果省掉每次约 4 µs。

### 6.7 小结

| 场景 | 每个 AE 节点每帧增加的代价（不含插件自身计算） |
|---|---|
| 不用 AE 插件的工程 | **0**（不加载、没有 CPU 节点、没有同步点） |
| 在匹配框架（Metal / D3D12）上运行的 GPU AE 效果 | 只有 GPU 上 RGBA16F ↔ BGRA128 的转换：几微秒；没有 CPU 传输 |
| CPU AE 效果，1080p，Apple Silicon（统一内存零拷贝） | 1.1 ms（8 位）– 2.0 ms（32 位） |
| CPU AE 效果，2160p，Apple Silicon（统一内存零拷贝） | 2.8 ms（8 位）– 6.6 ms（32 位） |
| CPU AE 效果，独立显卡（估算） | 约 1 ms（1080p 8 位）– 约 15 ms（2160p 32 位） |
| + 进程外，共享暂存内存（R01-02、R04-06） | 每次调用 / 回调 + 约 4 µs |
| + 进程外，朴素的额外拷贝 | + 0.5 ms（1080p 8 位）– 6 ms（2160p 32 位） |

## 8. `bae-aex-host` 骨架

`crates/bae-aex-host` 只放翻译层的**数据结构和纯转换函数**。它不加载任何东西、不链接任何 Adobe 的东西，没有 FFI，没有 `unsafe`（`#![forbid(unsafe_code)]`），唯一的依赖是 `bae-model`（02，无 GPU），用来在编译期核对参数映射。

### 8.1 构建与测试

```sh
cargo test   -p bae-aex-host
cargo clippy -p bae-aex-host --all-targets -- -D warnings
# GPU 往返基准（独立 package，有自己的工作区；wgpu =30.0.2）：
cargo run --release --manifest-path crates/bae-aex-host/bench/roundtrip/Cargo.toml [-- --quick]
```

### 8.2 设计规则

1. **只在用到的地方付出代价。** 不用 AE 插件的工程的渲染热路径上，碰不到这里的任何东西（§6.5）。
2. **BAE 自己的命名。** 每个类型都由 BAE 命名和设计。AE 标识符只出现在文档里，作为对照公开指南的交叉引用。没有任何结构体与 AE 结构体布局兼容；P3 的 FFI 层负责转换。
3. **没有 ABI 常量。** 选择器编号、标志位位置、错误码数值和 suite 名字符串刻意不写，等合规评估（§7）决定 P3 的 FFI 层怎么获得它们。
4. **纯函数、可测试。** 转换（时间、定点数、像素、标志 → 渲染需求、协议顺序、参数 → `EffectDef`）都是带单元测试的纯函数。
5. **与 19 的接口自动核对。** `selector` 和 `caps` 的测试读取 `sdk/c/bae_plugin.h`，回调名和线程级别对不上时测试失败。

### 8.4 已知与指南不一致之处（P3 开工时修正）

附录在各节末尾逐条核对了骨架与公开指南（附录 §2.12、§3.9、§5.15、§6.14、§13.6、§15.8、§16.9）。主要的几处：几个选择器的线程归属写成了"渲染线程"，指南说是界面线程；`MatchName` 应只接受 7 位 ASCII，并识别 `ADBE ` 前缀；一个模块应能有多个描述（多 PiPL）；`ParamDescriptor` 的 disk id 回退规则应按整个列表（第一个 id 为 0 时整体编号）；图层参数应带"取哪一级结果"（源 / 蒙版后 / 效果后）；能力标志应区分静态和动态。这些都不影响 02/04/19 的接口，只影响兼容层内部，留到 P3 实现时一并修正。

## 9. 分阶段计划

| 阶段 | 里程碑 | 内容 | 前提 |
|---|---|---|---|
| **P1（现在，0.0.1）** | M1 | 本文；`bae-aex-host` 骨架（数据结构、纯转换、与 19 C ABI 的自动核对、`EffectDef` 转换）；GPU 往返基准；对 02/04/19/06/12/15 的预留请求 | 合规关卡 G0 |
| **P2（随各工作流推进）** | M1–M2 | 各负责人处理 §5 中标为"现在"的请求：02 的参数模型补全和引用语义、04 的按需拉取与不死锁、06 的工作空间描述、19 的动态贡献和辅助进程能力形状、12 的界面位置。20 跟进核对，接口变化时更新骨架和测试。 | — |
| **P3a：可行性验证** | M3 | 用公开资料完成 PiPL 静态解析（不执行代码）和扫描缓存；用真实工程统计第三方效果的使用情况，确定先做哪一级（§3.15，§10 Q5）；向法务提交附录 §21.13 的证据包 | G1 |
| **P3b：A 级原型** | M3 | 单独分发的插件包 `bae.aex-compat`：适配器 + `bae-aex-runner` 辅助进程；SmartFX 与旧式 CPU 渲染、参数、序列数据、多帧渲染、逐像素 suite；只在实验室用获准的插件测试 | G2、G3 |
| **P3c：B / D 级** | M3 之后 | 自定义界面（ABI 0.2 的 `ui_event` / `bae.draw`）、选项与许可窗口、计算缓存、只读场景 API（`bae.scene`） | 19 ABI 0.2 |
| **P3d：C 级（GPU）** | 视需要 | 进程内 Metal / D3D12 GPU 效果；评估跨进程 GPU 共享（R01-02） | 用户信任模型定稿 |
| **公开发布** | — | 只有在 G4、G5 回答完、并有经过测试的兼容列表之后，才能公开发布兼容层或做"兼容"声明 | G4、G5 |

每个阶段都遵守 §1 的原则：不用 AE 插件的工程没有任何代价；数据永不丢失；在合规关卡回答之前不越界。
